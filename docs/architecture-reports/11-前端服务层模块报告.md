# 11 - 前端服务层模块报告

> 模块路径：`frontend/apps/web/src/services/`  
> 分析文件：`content.ts`, `github.ts`, `links.ts`, `stats.ts`, `works.ts`

---

## 1. 模块职责

服务层模块封装了对后端 API 的调用：
- `content.ts`：内容管理 API
- `github.ts`：GitHub API 集成（作品同步）
- `links.ts`：导航链接 API
- `stats.ts`：统计数据 API
- `works.ts`：作品管理 API

---

- ✅ 文件名语义清晰

### 注释质量

---

## 3. 架构合理性评估

### ⚠️ 中等问题

1. **服务层与 API Route 重复**
   - `services/` 层直接调用后端 API
   - `app/api/` 层也调用后端 API
   - 两层的职责边界不清晰
   - **建议**：明确职责 - services 面向客户端组件，api routes 面向外部请求

2. **缺少统一的 HTTP 客户端**
   - 每个服务文件独立使用 `fetch()`
   - 没有统一的 Base URL、超时、重试配置
   - **建议**：创建统一的 `apiClient` 实例

3. **缺少 TypeScript 泛型**
   - API 响应类型未使用泛型封装
   - 每个服务手动定义响应类型

### 🟠 低优先级

4. **缺少请求取消**
   - 没有 AbortController 支持
   - 组件卸载时请求不会被取消

5. **缺少错误码映射**
   - 直接返回后端错误消息
   - 前端需要根据消息内容判断错误类型

---

## 4. 发现的问题和缺陷

| # | 严重程度 | 问题描述 |
|---|---------|---------|
| 1 | 🟡 中 | 服务层与 API Route 层职责重叠 |
| 2 | 🟡 中 | 缺少统一 HTTP 客户端 |
| 3 | 🟠 低 | 缺少请求取消支持 |
| 4 | 🟠 低 | 缺少错误码映射 |

---

## 5. 改进建议

1. **创建统一 HTTP 客户端**：
   ```typescript
   const apiClient = {
     async get<T>(url: string): Promise<T> { ... },
     async post<T>(url: string, body: unknown): Promise<T> { ... },
   };
   ```

2. **明确层间职责**：services 面向组件，api routes 面向 SSR/外部

---

## 6. 总结

服务层结构基本合理，主要改进方向是创建统一的 HTTP 客户端和明确与 API Route 层的职责边界。
